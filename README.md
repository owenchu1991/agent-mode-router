# Agent Mode Router

**Agent Mode Router** 是专为 **Google Antigravity** 设计的智能任务诊断与执行策略路由 Skill。

面向所有用户（包括不具备编程背景的用户），自动识别软件开发任务的**技术不确定性、可拆分性、模块耦合度、持续周期、变更风险与多 Agent 协调开销**，在 Antigravity 官方支持的执行模式（**Default Agent**、**Subagents**、**/plan**、**/boost**、**/swarm**、**/teamwork**、**/goal**、**/grill-me** 及动态阶段组合）中推荐最合理、最高效、成本适当的执行策略，并生成可直接复制使用的原生指令。

---

## 🌟 核心特性与设计哲学

1. **大白话决策解释**：面向非技术用户，使用通俗、客观的语言说明为何该模式最适合，严禁故弄玄虚堆砌术语。
2. **纯策略诊断，绝不乱改代码**：仅进行只读代码检查与策略建议，不擅自修改工程代码，不盲目启动高成本多 Agent。
3. **原生命令边界清晰**：明确区分 Skill 策略编排与 Antigravity 原生命令（`/boost`、`/swarm` 等）的边界，不假装文字输出即已启动模式。
4. **严格的生命周期退出门禁 (Gate Conditions)**：严格区分规划（Plan）、诊断（Diagnosis）、实施（Implementation）与验收（Acceptance）。**每个阶段门禁仅包含该阶段能交付的产物，严禁要求 Plan 阶段产出代码**。
5. **性能诊断与架构重构解耦**：坚持“实测证据驱动”，优先采集性能 Profile 证据，严禁在缺乏数据支撑前假定某种架构修改一定能提升性能。
6. **信息事实分层与零虚构**：
   - 严格区分【用户明确事实】、【代码验证事实（附文件证据）】与【待验证假设】。
   - 严禁编造“提速 60%”等虚假数据，禁止使用“必然造成冲突”等绝对化断言。
7. **拒绝固定套路，拥抱动态演进**：废弃机械的 `Plan → Boost → Swarm` 固定链条，每个阶段依据真实产物与验收结果动态路由下一步。
8. **Swarm 协调成本门禁**：仅在文件正交、接口锁定且并行收益预计明显超过多 Agent 广播与合并成本时，才推荐 `/swarm`。
9. **强制竞争模式对比**：每次路由均提供首选模式与最具竞争力的替代模式，详细分析关键取舍（Trade-offs）。

## 🧭 支持的 Antigravity 执行模式一览

| 模式 | 核心定位与适用场景 | 关键约束与取舍 |
| :--- | :--- | :--- |
| **Default Agent** | 普通开发、单点修复、局部 UI/样式调整、单一独立功能开发。 | **首选默认项**。单线直行、零通信损耗，适合边界清晰、无深度分歧的场景。 |
| **Subagents** | 委派独立、轻量、只读或沙箱化辅助任务（如只读代码审查、测试运行）。 | 辅助委派机制，用于保持主会话清洁，而非全局架构决策。 |
| **`/plan`** | 规划与方案设计。需求未梳理、架构需调整、高风险重构或需前置方案审批。 | **交付物仅限文档与接口契约**，不能直接改代码；已有明确方案时不应重复 Plan。 |
| **`/boost`** | 深度攻坚。解决高技术不确定性、未知根因排查、多方案竞争推演与多轮实验验证。 | **深度探索主力**：具备完整代码与测试能力，非“只动脑不写代码”。高不确定性时首要权衡模式。 |
| **`/swarm`** | 独立解耦单元并行协作。多工作单元接口已锁定、文件归属正交的批量交付。 | **协调开销大**：依赖未定的模块严禁 Swarm；必须确保并行提速大于集成与广播看板成本。 |
| **`/teamwork`** | 跨阶段长周期工程管理。包含多阶段演进、明确角色分工与严格阶段审计。 | 流程与管理开销重；中小型项目或短期迭代严禁滥用 Teamwork。 |
| **`/goal`** | 目标与验收标准极为清晰，需在授权边界内自主循环重试、减少中途打扰。 | 解决长程自主闭环，而非疑难技术攻坚；不可绕过安全权限。 |
| **`/grill-me`** | 关键业务需求、用户体验路径或产品形态不明确，需用户参与决策。 | 交互式对齐业务决策；**严禁询问可从代码中查明的问题**。 |

## 📦 安装与配置方法

### 方法一：安装到当前项目工作区（推荐）
在您的项目根目录下克隆本仓库至 `.agents/skills/agent-mode-router`：

```bash
mkdir -p .agents/skills
git clone https://github.com/owenchu1991/agent-mode-router.git .agents/skills/agent-mode-router
```

### 方法二：全局安装（所有项目通用）
克隆至您的全局 Antigravity 配置目录：

```bash
mkdir -p ~/.gemini/config/skills
git clone https://github.com/owenchu1991/agent-mode-router.git ~/.gemini/config/skills/agent-mode-router
```

## 🚀 使用指南

### 1. 自动触发
当您在 Antigravity 对话中提出复杂工程任务、多模块重构、疑难 Bug 或不确定该怎么推进时，Agent 会自动调用此 Skill 为您诊断：
> “我要重构整个材质渲染系统，目前核心架构有循环依赖，同时需要开发 3 种新材质，该怎么推进？”

### 2. 显式调用（Slash Command）
您可以直接输入 `/agent-mode-router` 并描述您的需求：
```text
/agent-mode-router 我正在开发一个基于 Three.js 的编辑器，遇到 Android 端掉帧但原因不明，请帮我评估应该用什么模式。
```

### 3. 标准输出示例
```markdown
### 1. 任务事实与现状诊断
*   **用户明确事实**：所有 28 款表盘受影响组件均调用公用时间格式化函数 formatClockTime()。
*   **代码验证事实**：已通过检查确认时间格式计算集中于单一工具函数，无组件独立实现。
*   **待验证假设**：上游传入参数符合标准格式（待单元测试验证）。

### 2. 模式推荐与取舍对比
*   **推荐模式：** Default Agent（普通直接执行）
*   **最具竞争力的替代模式：** /swarm
*   **两者的关键取舍 (Trade-offs)**：
    *   *选择 Default Agent 的理由*：表面涉及 28 个表盘，实为单点缺陷（Single Point of Failure）。单 Agent 修改单个函数并运行测试，响应最快、成本最低。
    *   *不选 /swarm 的原因*：无独立工作单元可拆分，派发多 Agent 修改同一文件会导致严重的协同开销与代码冲突。
*   **是否需要先 Plan：** 否（纯函数局部逻辑修复，无需架构规划）。

### 3. 当前阶段核心目标与退出门禁 (Gate Conditions)
*   [ ] 补充边界时间点的单元测试用例。
*   [ ] 修复 24 小时制取模逻辑。
*   [ ] 回归测试通过，确认 12h/24h 均正常。

### 4. 下一步原生命令
请复制并在 Antigravity 输入框中执行以下命令：
> 修复 formatClockTime() 中的 24 小时制逻辑，先补充单元测试用例，再进行修复并运行回归测试。
```
