# 十大经典测试案例诊断与验证记录

本文件记录了 `agent-mode-router` 在十大基准案例中的诊断推导逻辑、六维评估结果、候选模式取舍与标准输出对比，作为 Skill 规则验证与回归测试的基准。

## 案例 A：局部样式微调
- **用户输入**：“帮我把按钮的圆角从 8px 改成 12px。”
- **六维评估**：
  - 技术不确定性：低
  - 任务可拆分性：低（无需拆分）
  - 模块耦合：低
  - 持续性：单次极简任务
  - 风险：极低
  - 成本收益：多 Agent 毫无收益，且引入多余调度开销
- **规则应用**：规则 1（简单任务优先轻量执行）
- **输出结果**：
  - **推荐模式**：Default Agent（普通直接执行）
  - **最具竞争力的替代模式**：Subagents（不推荐，单行样式修改无需额外子会话隔离）
  - **理由**：修改目标单一明确，范围完全局部，普通会话可即时完成，无需多 Agent 协调或额外规划流程。
  - **是否需要先 Plan**：否。
  - **下一步指令**：直接在输入框发送：“帮我把按钮的圆角从 8px 改成 12px。”

## 案例 B：多设备疑难兼容与性能卡顿
- **用户输入**：“WebGL 材质效果在部分安卓设备上卡顿，已经尝试多种方法，仍然找不到原因。”
- **六维评估**：
  - 技术不确定性：高（根因未知、设备碎片化严重、前期经验排查未生效）
  - 任务可拆分性：低（在未定位根本性能瓶颈前，无法安全拆解独立实施单元）
  - 模块耦合：中～高（着色器指令、纹理显存与渲染上下文交织）
  - 持续性：单次探索与优化
  - 风险：中（可能引发视觉渲染降级）
  - 执行成本：需多假设推演与针对性测量
- **规则应用**：规则 2（技术不确定性主导，深入对比 Boost 与 Default Agent）
- **输出结果**：
  - **推荐模式**：`/boost`
  - **最具竞争力的替代模式**：Default Agent
  - **关键取舍 (Trade-offs)**：
    - *选择 Boost*：用户已尝试多种方法仍未定位根因，说明存在多变量交织。Boost 能多视角提出相互竞争的假设（如浮点精度、GPU 批处理中断、纹理带宽），并通过设计对照基准实验完成假设-验证闭环。
    - *不选 Default Agent*：Default Agent 偏向单线经验试错，在复杂多机型图形兼容性场景下容易陷入反复猜测。
  - **是否需要先 Plan**：否。此时首要矛盾是缺乏实测证据，静态规划无法替代动态根因诊断。
  - **下一步指令**：
    ```
    /boost 深入排查 WebGL 材质在部分安卓机型上的卡顿问题：提出多种潜在根因假设（着色器浮点精度、纹理带宽、Draw Call 打断），设计对照测试用例收集性能基准数据，定位瓶颈并验证优化方案。
    ```

## 案例 C：接口已固化的多模块并行开发
- **用户输入**：“按照已经确定的设计规范，同时开发背景材质、前景材质、预设列表和参数编辑器，相关接口已经稳定。”
- **六维评估**：
  - 技术不确定性：低（规范与方案已确定，无重大技术盲区）
  - 任务可拆分性：高（4 个工作单元边界清晰、文件独立）
  - 模块耦合：低（公共接口已固定，各自文件归属明确）
  - 持续性：单次并行交付
  - 风险：低
  - 执行成本与协调开销：由于文件完全正交且契约明确，并行收益明显高于任务切分与合并成本
- **规则应用**：规则 3（可并行工作量主导，满足 Swarm 协调门禁）
- **输出结果**：
  - **推荐模式**：`/swarm`
  - **最具竞争力的替代模式**：Default Agent（单线按清单顺序开发）
  - **关键取舍 (Trade-offs)**：
    - *选择 Swarm*：接口与文件归属完全锁定，4 个 Worker 各自独立编写对应模块，可显著缩短总日历工期。
    - *不选 Default Agent*：单 Agent 串行虽无多 Agent 协调开销，但多模块排队等待时间长。
  - **是否需要先 Plan**：否。现有设计规范与接口已经锁定，无需重复规划。
  - **下一步指令**：
    ```
    /swarm 根据已确定的设计规范与稳定接口，创建 4 个并行工作单元分别实现：1. 背景材质模块 2. 前景材质模块 3. 预设列表模块 4. 参数编辑器模块，并附带各自模块的单元测试。
    ```

## 案例 D：全生命周期大型工程
- **用户输入**：“我想从零开发一个完整的跨平台表盘编辑器，涵盖渲染、编辑、导出、存储、测试等系统。”
- **六维评估**：
  - 技术不确定性：中～高（跨平台抽象与渲染引擎选型）
  - 任务可拆分性：高（系统级工程拆解）
  - 模块耦合：高（子系统间需要全局架构约束）
  - 持续性：高（长周期、多里程碑、跨阶段持续维护）
  - 风险：高（底层架构失误会波及全局）
  - 执行成本：需持续的项目管理机制
- **规则应用**：规则 4（长周期工程优先 Teamwork）
- **输出结果**：
  - **推荐模式**：`/teamwork`
  - **最具竞争力的替代模式**：`/plan` 结合分步执行
  - **关键取舍 (Trade-offs)**：
    - *选择 Teamwork*：工程涵盖 5 个大子系统，需要经历架构确立、模块施工、多端适配与集成验收等多个独立里程碑，具备长周期跨角色演进特征。
    - *不选直接 /swarm*：从零起步工程在顶层架构未稳定前，简单并行会导致子系统间契约无法对齐，后期集成与重构成本极高。
  - **是否需要先 Plan**：包含在 Teamwork 首个里程碑内。
  - **下一步指令**：
    ```
    /teamwork 启动跨平台表盘编辑器工程：建立架构规划、渲染管线、编辑画布、导出适配、持久化存储与集成测试等全生命周期里程碑，并分阶段推进交付。
    ```

## 案例 E：高耦合重构与新需求混合
- **用户输入**：“重构整个材质渲染系统，目前核心架构有问题，多个模块互相依赖，同时需要开发新功能。”
- **六维评估**：
  - 技术不确定性：高（核心架构存在缺陷，重构路径未明）
  - 模块耦合：高（模块间存在双向依赖）
  - 关键路径：必须先梳理依赖拓扑与解耦协议，方可安全实施代码重构。
- **规则应用**：规则 5（核心架构依赖优先 /plan）
- **输出结果**：
  - **推荐模式**：`/plan`
  - **最具竞争力的替代模式**：`/boost`（深入排查架构调用瓶颈）
  - **关键取舍 (Trade-offs)**：
    - *选择 Plan*：当前核心阻塞是模块间相互依赖与结构混乱。Plan 聚焦于输出依赖关系图谱、模块分层方案与接口契约文档，为后续安全重构提供蓝图。
    - *不选直接 /swarm*：在模块边界和接口尚未解耦前，并行开发存在高概率合并冲突（触发条件：多个 Worker 同时修改共用状态与依赖文件；缓解措施：先通过 Plan 划定文件归属与单向依赖流）。
  - **是否需要先 Plan**：**是**。方案前置规划能明确依赖顺序，降低无效返工。
  - **当前阶段退出门禁 (Gate Conditions)**：
    - [ ] 产出模块间依赖拓扑分析与循环依赖解耦方案文档。
    - [ ] 产出统一公共接口契约定义。
    - [ ] 用户确认方案合理性。（*注意：代码实际改造由后续实施阶段完成*）
  - **下一步指令**：
    ```
    /plan 针对现有材质渲染系统的架构缺陷进行解耦规划：分析模块间相互依赖关系，输出清晰的分层重构方案与公共接口定义文档，规划分步实施与新功能接入路线。
    ```

## 案例 H：跨多文件的复杂异步竞态 Bug
- **用户输入**：“修复一个涉及十几个文件的复杂竞态问题。”
- **六维评估**：
  - 特征：表面涉及十几个文件，但核心是“异步竞态”，属于典型的高度技术不确定性与时序耦合问题。
- **规则应用**：规则 2（技术不确定性主导优先 Boost，防误判规则：绝不因涉及文件多就推 Swarm）
- **输出结果**：
  - **推荐模式**：`/boost`
  - **最具竞争力的替代模式**：Default Agent
  - **关键取舍 (Trade-offs)**：
    - *选择 Boost*：竞态问题强依赖全局时序与异步事件链，根因隐蔽。Boost 能够多视角追踪调用链路，建立假设竞争模型并构造可复现的并发测试用例。
    - *不选 /swarm*：文件虽多但逻辑高度耦合。拆分多个 Worker 修改不同文件极易加剧状态不一致，甚至引入新的死锁。
  - **是否需要先 Plan**：否。此时需要的是动态时序排查与验证实验，静态方案无法替代根因分析。
  - **下一步指令**：
    ```
    /boost 深入排查跨多文件的异步竞态 Bug：分析事件总线、状态同步机制与异步时序边界，构建可复现竞态条件的并发测试用例，并完成针对性修复与验证。
    ```

## 案例 I：单一组件开发且要求测试闭环
- **用户输入**：“开发一个组件，要求完成后自动测试，确认无误再结束。”
- **六维评估**：
  - 特征：单一组件、目标清晰、验收标准明确（自动化测试全绿）。
- **规则应用**：规则 1（轻量执行）或自主闭环需求强时选 `/goal`
- **输出结果**：
  - **推荐模式**：Default Agent（或 `/goal`）
  - **最具竞争力的替代模式**：`/goal`（若用户希望 Agent 自主循环测试与调试、减少中途打扰，可选择 /goal）
  - **关键取舍 (Trade-offs)**：
    - *选择 Default Agent*：单一组件任务范围明确，单 Agent 编写代码并运行测试用例足够高效，无额外调度负担。
    - *不选 /swarm*：单一组件无法正交拆分为多个独立 Worker，滥用多 Agent 属于过度工程化。
  - **是否需要先 Plan**：否。
  - **下一步指令**：
    ```
    开发该组件并为其编写单元测试，执行自动化测试直至全部用例通过。
    （如需自主闭环无人打扰模式，可使用：/goal 开发该组件并编写对应自动化测试，反复调试验证直至所有测试通过后再退出）
    ```

## 案例 J：强依赖未决共享模型的四模块任务
- **用户输入**：“需要同时开发四个模块，但它们都依赖一个还没确定的公共数据模型。”
- **六维评估**：
  - 核心特征：下游 4 个模块看似可并行，但上游公共数据模型未定。
  - 关键路径：基石模型必须先行锁定，否则各模块因数据结构假设不一致将面临高概率代码废弃。
- **规则应用**：规则 5（前置公共依赖未定时优先 /plan 规划契约）
- **输出结果**：
  - **推荐模式**：`/plan`
  - **最具竞争力的替代模式**：Default Agent
  - **关键取舍 (Trade-offs)**：
    - *选择 Plan*：首要阻塞是“公共数据模型与类型契约未确定”。通过 Plan 锁定数据字段与调用接口规范，为后续模块开发建立坚实底座。
    - *不选立即 /swarm*：在公共契约未建立时提前并行，各 Worker 产生的数据结构存在高冲突风险（触发条件：依赖尚未定义的公共状态；缓解措施：先由 Plan 产出接口定义，通过验收后再行分工）。
  - **是否需要先 Plan**：**是**。
  - **当前阶段退出门禁 (Gate Conditions)**：
    - [ ] 产出公共数据模型字段规范文档与类型定义声明。
    - [ ] 产出 4 个模块对公共数据模型的依赖协议与入参出参说明。
    - [ ] 用户确认数据模型合理性。
  - **下一步指令**：
    ```
    /plan 针对计划开发的四个模块，优先梳理并定义核心公共数据模型、数据流转逻辑以及跨模块调用契约，明确各模块的依赖接口规范文档。
    ```
