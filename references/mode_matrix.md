# Antigravity 执行模式全维度对比矩阵

| 模式名称 | 核心定位 | 典型收益 | 协调与额度成本 | 适用前提与前置条件 | 典型误区与禁止场景 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Default Agent** | 单会话标准执行 | 极低延迟，无额外上下文开销，沟通成本最低 | 最低 (1x 基础 Token) | 目标明确、影响范围局部、技术风险可控 | 滥用多 Agent 处理常规单文件或简单多文件编辑 |
| **Subagents** | 局部子任务委派 | 隔离长文本研究/搜索/测试结果，保持主会话清洁 | 低～中 (按需启动单次子会话) | 存在明确、独立的只读调研、测试执行或沙箱交互 | 把它当成重型架构工具，或在无需隔离的小查找中过度委派 |
| **`/plan`** | 实施方案前置规划 | 梳理技术路径，暴露潜在风险，供用户提前审核，避免无效代码返工 | 低 (纯规划与方案文档生成) | 需求尚未理清、架构需大改、存在高风险变更、或需前置审批 | 只要有多个模块就一律强制 /plan；在已有明确计划时重复 /plan；**把代码实现当成 Plan 的退出门禁** |
| **`/boost`** | 深度探索与攻坚 | 多视角思考、深层根因排查、多假设验证与自动化测试闭环 | 中～高 (深度推理与多轮验证) | 技术方案未知、Bug 根因隐蔽、多变量交织疑难问题 | 误以为 Boost“只动脑不写代码”；无理由将 Boost 降级为备用方案 |
| **`/swarm`** | 独立解耦单元并行协作 | 多 Worker 并行交付，缩减日历总工期 | 极高 (多 Agent 广播共享看板，重度消耗配额与协调开销) | 方案已定、模块边界与文件归属完全解耦、公共接口已锁定 | 核心架构未定即盲目并行；多 Worker 修改同一组文件导致代码冲突；**在协调成本高于并行收益时盲目推荐** |
| **`/teamwork`** | 跨阶段长周期工程管理 | 自动化多阶段演进、角色分工明确、里程碑阶段验收审计 | 高～极高 (长期运行项目看板与多角色维护) | 大规模跨子系统重建、长期迁移工程、需要多里程碑阶段审计 | 普通功能开发或短期重构；将原本较短周期的迭代扩大为全套流程 |
| **`/goal`** | 长程自主闭环执行 | 减少中途打扰，自主循环重试与测试，直到满足明确验收标准 | 中～高 (持续循环与自主验证) | 目标高度确定、验收测试标准明确可自动判定、夜间或无人值守 | 技术方案未决的盲目试错；涉及敏感生产数据或需人工安全确认的高危操作 |
| **`/grill-me`** | 业务与产品设计对齐 | 通过交互式访谈引导用户澄清业务逻辑与体验细节 | 低 (纯对话对齐) | 业务方向、产品需求或用户体验边界模糊，需人工决策 | 询问能直接从代码/配置文件中自动推断的技术细节（如端口、依赖包版本等） |

## 核心机制深入对比

### 1. 技术不确定性下的核心权衡：Boost vs Default Agent
当面对未知根因（如移动端掉帧、竞态条件、内存泄漏）时：
*   **选择 Boost 的适用场景**：
    *   存在多种相互冲突的假设（例如 Shader 复杂度 vs 纹理显存带宽 vs CPU DrawCall 批处理）。
    *   需要从多个工程视角（渲染管线、设备驱动、内存拓扑）系统性发散与排查。
    *   需要编写针对性的探针、基准测试用例，并进行假设-验证-修正的闭环循环。
*   **选择 Default Agent 的适用场景**：
    *   问题范围相对聚焦，排查线索明确，单线排查即可快速定位。
    *   团队已有清晰的调试思路，仅需按部就班打印日志或二分定位。
*   **结论**：Boost 是高技术不确定性场景下的第一梯队核心模式，绝非次要备选。

### 2. 并行开发的经济学：Swarm 协调成本门禁
多 Agent 并行绝非“免费的加速器”，它带来显著的额外协调成本：
1.  **任务拆分与上下文开销**：每个 Worker 启动需要独立的上下文注入与 Brief 编写。
2.  **看板通信开销**：在共享消息看板上，每个 Worker 的输出都会被其他 Worker 和协调者阅读，Token 消耗呈指数级增长。
3.  **接口契约摩擦**：若各模块并非 100% 独立，稍微存在的隐式约定变动都会引发集成冲突。
4.  **合并与回归成本**：并行修改的代码最终需要合并回主分支，可能需要人工解决集成差异。
*   **Swarm 准入原则**：只有当并行带来的日历时间收益明显超过上述协调与集成成本时，才推荐 Swarm。若收益边缘化，Default Agent 单线按清单交付不仅总 Token 消耗更低，且稳定性更高。

### 3. 性能诊断与架构重构的解耦原则
*   **严禁因果倒置**：不能在没有性能 Profile 证据的情况下，主观认定“现有的架构必然是性能杀手，重构架构就能自动解决卡顿”。
*   **正确工序**：
    1.  **证据收集**：先通过针对性性能分析（如 GPU Timer、Draw Call 计数、显存监控）抓出真实瓶颈。
    2.  **根因定位**：确认瓶颈到底是局部资产（如某张超大贴图、未压缩的顶点属性）还是架构设计（如频繁切换管线状态）。
    3.  **决策驱动**：若瓶颈只是局部资产，无需兴师动众重构架构；若证实是架构问题，再将性能约束纳入架构重构方案中。

## 降级与兜底策略 (Fallback Guidance)

在实际使用中，若遇到用户环境受限或无高级模式配额，可按以下路径平滑降级：

1. **/swarm 配额不足或不可用**：
   - 降级为：`Default Agent + 分步执行清单`。
   - 策略：先由 Agent 生成按模块拆分的清单，然后逐个模块单线程实现并运行测试。虽然耗时变长，但代码质量和边界隔离依然可控。
2. **/boost 额度受限**：
   - 降级为：`/plan` 辅助生成假说矩阵 $\to$ `Default Agent` 单步验证假说。
3. **/teamwork 模式未启用**：
   - 降级为：`/plan` 生成阶段化 Milestone $\to$ 配合普通对话分阶段验收交付。
